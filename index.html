About this seed

Crawler change

On 27 Sep 2026 at 21:28 UTC the seed switched to new crawler software, LionSeed.

what is this?

Figures from the 21:43 UTC sample onward come from the new crawler. It started with a shorter history than the old one, so the counts stepped down at the switch and will rebuild over roughly two days. That drop is the change of crawler, not nodes leaving the network. The new crawler also reaches Tor and I2P nodes, so from that point the post-fork counts include them. The stable nodes list below restarted its observation period at the switch as well.

Scope

Two limits, both of which make these numbers a lower bound.

what is this?

First, a crawler only sees nodes that accept incoming connections. Anything behind NAT that never listens is invisible to it. Second, “rated good” is the seeder’s own quality gate: the node answered a handshake in the last hour, on the right port, with the right services and height, and has a solid uptime record. A node that is up but new to the crawler, or that dropped out recently, is not counted yet. Treat the good count as “confidently serveable”, not as “every node that is up”.

How this is measured — what is this?
How this is measured
  • A crawler connects to each node on port 8333 and completes a Bitcoin handshake, recording the services, block height and software it reports. Nothing here is second-hand.
  • Post-fork nodes are identified by service bit 28 (0x10000000, NODE_BLAKE2B), taken only from the node’s own handshake, never from addresses gossiped by other peers.
  • Clearnet, Tor and I2P nodes are all crawled (Tor and I2P since 27 Sep 2026).
  • A node reporting the post-fork bit while running software with no BLAKE2b support is still counted, but flagged, since it is either misconfigured or misreporting.
  • “Rated good” is conservative. It is the seeder’s internal gate: a handshake within the last hour, correct port, advertised services, protocol version, reported block height and a sustained uptime history. Post-fork nodes are re-checked every 15 minutes. A node can be reachable and still not clear it yet, for example if the crawler has only just found it, so the honest reading is “at least this many”.
  • Regenerated hourly. The timestamp above is when the figures were taken, not when you opened the page.

Are nodes agreeing on the chain?

what is this?

Each node reports its block height during the handshake. A cluster stuck well behind the rest is the first visible sign of a chain split — so the post-fork nodes are split here into those on an enforcing release and those not, to show whether the two groups are drifting apart.

why heights can look spread out

Heights are as of each node's last handshake, not this instant, so some of the spread is crawl recency rather than real lag. A genuine split would show as a persistent cluster in the bottom row across several updates.

Stable nodes list, for fixed-seed runners

what is this?

If you run a curated, fixed-list seed rather than a crawler, the hard part is knowing which nodes are actually reliable. This is that evidence: post-fork nodes this crawler has found consistently reachable, with the figures behind the claim.

Read first

This is evidence to curate from, not a list to serve unexamined. A curated seed is resistant to Sybil attacks precisely because a human chooses it. An attacker cannot get in by running nodes. Serving this list verbatim would hand that property away, because anything that keeps its uptime high ends up here automatically. Use it to inform your judgement, not to replace it.
