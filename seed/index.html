Only fork nodes, under any query

Every service-bit filter of the form x<hex> is accepted, for example x10000009 (NODE_NETWORK|NODE_WITNESS|NODE_BLAKE2B) or x9. A bare hostname query uses x9.

Whatever the filter, the only nodes that can ever appear in an answer are nodes this seed has itself confirmed to be on the fork. So a bare or x9 query never returns a non-fork node. This is a deliberate deviation from stock seeder behaviour.

The reason: the fork shares port 8333 with the much larger SHA256d network. An unfiltered answer would be composed mostly of peers that are useless to a fork node.

How nodes are chosen

A node is served only when all of these hold:

  • The seed completed a handshake with it and the node advertised NODE_BLAKE2B (service bit 28) in its own version message. Service bits gossiped by other peers are never trusted on their own.
  • It reported a height of at least 961640 and advertises NODE_NETWORK.
  • It answered a handshake within the last hour. Fork nodes are re-checked every 15 minutes, so a node that goes away drops out of answers quickly.
  • It has a good reliability record over recent checks.

Each answer is a random selection of up to 24 of these nodes, at most one per /16 (IPv4) or /32 (IPv6) network, so no single provider can fill an answer. DNS answers carry clearnet addresses only. Tor and I2P nodes are crawled for the census and the crawl data, since DNS cannot carry those addresses.

The seed does not filter by user agent or node version. Any node that follows the fork's consensus rules is treated the same.

How to use it

Query the seed directly:

dig +short x10000009.seed.thelionpool.org

Or point a node at it:

bitcoind -seednode=seed.thelionpool.org

Software change, 2026-09-27

Until 2026-09-27 this seed ran a patched fork of sipa/bitcoin-seeder. On 2026-09-27 at 21:28 UTC it was replaced by LionSeed. The seed hostname, nameserver and IP address did not change.

The reason was the incident below. The old crawler worked through one queue shared with the whole SHA256d network, and the fork nodes kept getting starved. LionSeed schedules each node by what it already knows about it: fork nodes every 15 minutes, new addresses as soon as possible, non-fork nodes once a day. It also crawls Tor and I2P, which the old seeder could not.

Incident: served set collapse, 2026-09-20

This happened on the previous software.

For roughly 30 hours up to 2026-09-20 the seed's served set collapsed from 2967 nodes to 158, and DNS answers fell to 1 or 2 addresses.

Cause

The crawler selected nodes from a single FIFO shared with the whole SHA256d network. That queue held approximately 257,000 addresses while only about 400 of them were fork nodes. A full cycle took about 2.3 hours.

The seeder rated a node "good" using a decaying counter (tau = 2 hours) that required more than 2 observations. That means a node had to be polled at least every tau*ln2 = 83 minutes to stay rated. At a 2.3 hour cycle, fork nodes decayed out of the served set while still being perfectly reachable.

Fix

A second rotation queue was added for nodes confirmed to advertise NODE_BLAKE2B, given a fixed 5% share of crawl picks. Fork nodes polled within the 83-minute window went from 46 of 396 to 291 of 379, and DNS answers returned to a full packet. That fix shipped in the predecessor seeder (since retired in favour of LionSeed), which was then written so this kind of starvation cannot happen by design.

Policy compliance

Against doc/dnsseed-policy.md:

  • Results are crawled live. They are not biased or filtered per requester.
  • Each answer is a randomly selected subset of the currently good set, so two queries will usually differ. No requester or group of requesters is singled out to receive different results.
  • TTL is 60 seconds, the minimum the policy asks for.
  • DNS queries are not logged at all. The only per-requester state is a short-lived in-memory counter used for rate limiting, which is never written to disk.
  • Crawl data, meaning which nodes were reachable and when, is published through the census (point 5). It is not made more complete by biasing connectivity.
  • A contact address is published here, and is also in the zone's SOA RNAME.

No compliance is claimed beyond the points listed above.
